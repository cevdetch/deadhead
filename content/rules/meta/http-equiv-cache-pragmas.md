Cache values in `<meta http-equiv>` are cargo from the era when authors hoped the server would
turn markup into headers. `Cache-Control` and `Pragma` never became pragma-table keywords, and
neither did `Expires`. `ETag` and `Last-Modified` stayed out as well. No current server turns
markup into headers, and no current browser reads these tags: anything outside the pragma table
maps to no state. HTTP caching (RFC 9111) is driven by response header fields.

The usual copies try to stop caching: `<meta http-equiv="Pragma" content="no-cache">`,
`<meta http-equiv="Cache-Control" content="no-cache, no-store">` and
`<meta http-equiv="Expires" content="0">`, and the three can appear together. A page that
carries them is cached by the browser, by a CDN and by any proxy on the way, as the headers say.

## Why avoid

The tags are inert but not harmless. They are widespread: prevalence data finds `pragma` on
~391k sites and `expires` on ~387k, all non-standard. Each one tells the next maintainer that
caching is handled here, when it is handled, or mishandled, in headers. A stale-content bug then
gets debugged in the wrong file.

The caches that matter cannot read them. RFC 9111 defines caching on response header fields, so
a CDN or proxy that follows it decides from the headers, not from the HTML. The browser's own
cache stores the response under the same headers. A tag inside the document arrives too late and
in the wrong layer.

Even the `Pragma` header itself is deprecated, kept only for HTTP/1.0-cache backwards
compatibility; its meta shadow never had even that role. Validators were never document metadata
either: Roy Fielding's 1994 META proposal named `"Server", "Date", and "Last-modified"` as
http-equiv values that are "inappropriate", because those headers "should normally only be
generated by the HTTP server". `ETag` came later and belongs to the same group.

## Use instead

Delete the tags, and set the policy where caches read it:

```html
<!-- Before: no cache reads any of these -->
<meta http-equiv="Pragma" content="no-cache">
<meta http-equiv="Expires" content="0">
<meta http-equiv="Cache-Control" content="no-cache">
```

```http
Cache-Control: no-cache
ETag: "abc123"
```

`Cache-Control` alone covers current caches. `no-cache` lets a cache store the page and requires
it to revalidate before reuse, which an `ETag` or `Last-Modified` makes cheap; a `no-store`
keeps it out of caches entirely. `Expires` adds nothing beside it: RFC 9111 says that with
`max-age` present "a recipient MUST ignore the Expires header field", and treats an invalid
date, "especially the value "0"", as already expired.

## Detectability

The rule pre-filters with `meta[http-equiv]`: the verdict depends on whether the trimmed value,
compared ASCII case-insensitively, is one of the five cache keywords. The decision therefore
lives in `packages/rules/logic/meta/http-equiv-cache-pragmas.ts`. The CLI, the bookmarklet and
the ESLint plugin report the same findings, and none skips. The fix removes the element,
following the `meta/http-equiv-x-ua-compatible` precedent: nothing reads the tag, so deletion
loses nothing.

## Resources

- [HTML Standard: Pragma directives](https://html.spec.whatwg.org/multipage/semantics.html#pragma-directives): the pragma keyword table contains no cache entries; anything outside it maps to no state.
- [RFC 9111: HTTP Caching](https://www.rfc-editor.org/rfc/rfc9111.html#name-expires): caching runs on response header fields; `Expires` is ignored beside `max-age`, and "0" means already expired.
- [MDN: Pragma](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Pragma): deprecated; HTTP/1.0-cache backwards compatibility only; use Cache-Control.
- [MDN: Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control): `no-cache`, `no-store` and `max-age`.
- [W3C: META (proposed), 1994](https://www.w3.org/MarkUp/html-spec/Elements/META.html): "Server", "Date" and "Last-modified" named as inappropriate http-equiv values, headers "that should normally only be generated by the HTTP server".
