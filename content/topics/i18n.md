---
description: "Declaring a page's language for screen readers, browsers and search engines: lang on html, hreflang alternates, and the forms that fail quietly."
---

A page states its language once, with `lang` on `<html>`. Screen readers use it to choose
pronunciation rules, browsers use it for translation offers, hyphenation, font choice and
spell-checking, and the requirement is in WCAG as
[3.1.1 Language of Page](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html),
level A. Without it, a screen reader reads French text with English rules, or the other way
round.

A site in several languages also tells search engines which page serves which audience,
with `<link rel="alternate" hreflang>` pointing at each version. That markup fails quietly:
Google needs absolute URLs, and it matches codes against ISO 639-1 languages and ISO 3166-1
regions, so a relative `href` or a code such as `en-UK` drops a version from the set and
searchers can land on the wrong one. Google's
[localised versions guide](https://developers.google.com/search/docs/specialty/international/localized-versions)
documents the format.

Deadhead reports five ways to get language wrong:

- [`document/html-lang`](/rules/document/html-lang): no `lang` on `<html>`, or an empty one.
  Harmful, and missing on about one in fourteen of the
  [10,000 home pages](/blog/what-10000-home-pages-put-in-their-head) deadhead linted.
- [`link/hreflang-relative`](/rules/link/hreflang-relative) and
  [`link/hreflang-value`](/rules/link/hreflang-value): a relative URL or an unsupported code
  in an hreflang alternate.
- [`meta/google-value`](/rules/meta/google-value): `<meta name="google">` with a token Google
  does not read. Only `notranslate` and `nopagereadaloud` do anything.
- [`meta/http-equiv-content-language`](/rules/meta/http-equiv-content-language): the old
  pragma for the page language. Add `lang` before deleting it.

None of the harmful ones has an autofix: the repair is a language code or a URL only the
author knows.
